# V5.4 recovery runbook

This is a short guide for when something goes wrong in production. Each case says:
* how to see the problem;
* what to do first;
* what never to do.

The deploy mechanism behind cases A and B:
* A push to `main` runs `.github/workflows/deploy.yml`, then the root-owned `ops/deploy.sh`.
* `ops/deploy.sh` builds a candidate and runs a read-only health check.
* It switches only after 3 healthy observations. If the candidate fails, it rolls back automatically.

## Seeing the state

You can read the state even when the Hub domain is unreachable.

| Signal | Where |
| --- | --- |
| Deployed commit | Each runtime start writes an event: `payload.kind = 'runtime_started'`, with the `version` and code fingerprint.<br>The deploy run log on GitHub Actions and `/healthz` (`version`) show the deployed commit.<br>On a deploy's own start, the event's `version` still names the **previous** commit. `ops/deploy.sh` writes `deployed-sha` only after the new runtime is healthy, after it started. The `codeFingerprint` always identifies the running code: compare it with `node src/build-info.js <checkout of a commit>`. For example, `1082d172e32d5057` is `a8491e0`. |
| Everything at once | `ops/health-snapshot.sql`. It is read-only and returns one JSON row:<br>• runtime version and restarts<br>• last Office and coding activity<br>• worker heartbeats<br>• Continuity leases and handoffs<br>• failures in the last 24 h<br>• routes that are not healthy<br>• spend and budget periods<br>• pending owner items<br>• stuck objectives<br>• ops-watch alerts |
| Is the worker polling? | The Supabase edge logs. While the runtime and coding worker are up, they show about 200 requests every 5 minutes. |
| Owner alerts | The ops watch (`src/ops/ops-watch.js`) sends new findings to Telegram every 15 minutes:<br>• paid calls<br>• free-route incidents<br>• rejected keys<br>• capacity starvation<br>• blocked coding sessions<br>• the health probe |

## A. Bad UI deploy

* **You see:** a Hub screen is blank or broken, browser console errors, or a regression on Deliverables, Coding or the Office.
* **First,** with no deploy needed:
  * The old Hub stays at `/classic`.
  * Office → **Light** turns the 3D Office off.
* **Fix:** on GitHub, open the merged PR → **Revert** → merge the revert PR as a merge commit. The pipeline deploys the previous code and health-checks it.
* **Check:** `/healthz` `version`, or the newest `runtime_started` event, shows the revert commit.
* **Data:** UI changes have no data effects. Deliverable review rows can stay.
* **Never:** force-push `main`, or edit server files by hand while a deploy runs.

## B. Bad API or worker deploy

* **You see:**
  * `/healthz` is not OK, or `/api/*` returns 5xx;
  * the edge-log request rate drops to zero;
  * the health snapshot shows `errorEvents`, failed tasks, or `stuck.openObjectivesWithoutEventFor2h` above 0.
* **First:** `ops/deploy.sh` already rolled back a candidate that failed its checks. If the candidate passed but misbehaves, revert the PR as in A. Every deploy recreates the coding worker, so the revert restores it too.
* **V5.4 specifics:** both additions fail soft.
  * Without its migration, the budget rollover call returns false and changes nothing.
  * A failed `runtime_started` insert only logs a warning.

## C. Bad migration

* **Rules:**
  * Never edit an applied migration. Write the reverse as a new timestamped migration.
  * Apply a migration only with Fahad's approval.
  * Record the backup time before applying.
  * After applying, compare `list_migrations` and the schema fingerprint (`supabase/verify/README.md`).

The V5.4 migrations were applied on 2026-10-06, each verified on its own before the merge. Their reverses:

| Migration | Reverse |
| --- | --- |
| `20261005220000_create_hub_project_fix` | Re-create the function from `20260925160000_coding_agent_foundation.sql`. That brings back the known "column reference is ambiguous" defect, so only do it if the fix itself misbehaves. |
| `20261005230000_workspace_budget_rollover` | `drop function public.roll_workspace_budget_period(uuid);` The code tolerates the function being absent. |

* **V5.3** `deliverable_reviews` is additive. Drop it only if Fahad wants to discard his curation.
* **Data restore:** the Supabase daily backup restores the whole project, and PITR is off. Only Fahad decides a restore, and only as a last resort.

## D. Worker failure (Office runtime or coding worker)

* **You see:**
  * the edge-log rate drops;
  * there is no new activity while work is queued;
  * `/healthz` is red;
  * the container `Exited`. On 2026-10-03 the runtime was found `Exited (137)`.
* **Inspect,** on the VPS as root:
  * `docker compose -f /opt/fahad-ai-office/docker-compose.yml ps`
  * `docker compose -f /opt/fahad-ai-office/docker-compose.yml logs --tail=200 runtime` (or `coding-worker`)
* **Restart:**
  * `docker compose -f /opt/fahad-ai-office/docker-compose.yml up -d runtime`, or `restart coding-worker`.
  * Interrupted Office steps resume from their checkpoints.
  * Coding sessions resume from their last checkpoint once the old lease expires.
* **Switch the coding worker off:** `docker compose -f /opt/fahad-ai-office/docker-compose.yml stop coding-worker`.
* **Switch it on again:** `sudo bash ops/enable-coding-worker.sh`.
* **Never:** clear a lease by hand unless the old worker is confirmed stopped.

## E. Model or provider outage

* **Automatic:**
  * Free-first failover across the Model Pool, with per-route cooldowns in `provider_status`.
  * Office steps wait for capacity (`WAITING_FOR_CAPACITY`) and resume by themselves.
  * Coding sessions checkpoint before a provider switch.
  * The free-route guard blocks a billed "free" route for 24 h.
* **You see:**
  * `providers.notHealthy` in the health snapshot;
  * ops-watch alerts;
  * `model_attempts.failure_class`.
* **Kill switches,** with no deploy needed:
  * Exclude one route: add it to `workspace_routing_policies.excluded_routes`.
  * Turn a provider off: `update public.workspace_provider_permissions set enabled = false where provider = '<provider>';`
  * Remove a key: `sudo bash ops/set-secret.sh NAME` with an empty value.
* **Budget:** the workspace budget is monthly. With the V5.4 rollover migration, an ended period rolls over the next time the policy is read. The migration is applied: the V5.4 runtime rolled production to October on its first start (2026-10-06 14:26:51 UTC).

  Without that migration, an ended period refuses every paid reservation. On 2026-10-01 production hit exactly this. If the function is ever missing, Fahad can roll the period by hand:
  ```sql
  update public.workspace_policies
     set budget_period_start = date_trunc('month', now()),
         budget_period_end = date_trunc('month', now()) + interval '1 month',
         spent_usd = 0, version = version + 1, updated_at = now()
   where workspace_id = '2ae856da-00cb-4594-a7e6-710f2011d0c3' and now() >= budget_period_end;
  ```

## F. Continuity failure

* **Production today** (verified 2026-10-06, before and after the V5.4 deploy):
  * The Continuity Supervisor is **on**. Its 60-second lease poll shows in the Supabase edge logs as `rpc/freeze_stale_coding_leases`, and only the Supervisor calls that function. The first poll was at 2026-10-04 15:20:39 UTC, an hour after the Continuity stack (#102 to #106) was merged. It has run continuously since, through the V5.3 and V5.4 deploys. The certification report first said "off"; that read the historical notes in `AGENTS.md`, not production.
  * Only the native `office` worker is enabled in `coding_workers`.
  * There are 0 active `coding_leases` and 0 pending `coding_handoffs`.
* **If the Supervisor fails:**
  * Set `CONTINUITY_SUPERVISOR=false` and restart the runtime. Shutdown drains the Supervisor first.
  * Check `coding_leases` (`status = 'active'`) and `coding_handoffs` (not accepted).
  * Never reclaim a lease without proof that the previous writer stopped. The `WORKER_STOP_UNCONFIRMED` guard enforces this.
* **References:**
  * `docs/CONTINUITY-PHASE-N-READINESS.md` has the activation order and rollback.
  * The Continuity PR stack has its own rollback plan.

## G. Accidental test data

* **Prevention:**
  * Run tests in an isolated, clearly named project, such as "CERTIFICATION V5.4 (test, safe to delete)".
  * Put TEST or CERTIFICATION in the title.
  * Use `[free-only]`.
* **Removal:**
  1. Classify the rows in a manifest as CONFIRMED TEST, UNCERTAIN or CONFIRMED REAL.
  2. Write an explicit-ID cleanup script. Use `docs/v5.4-test-data-manifest.md` and `ops/cleanup/v5.4-test-data-cleanup.sql` as the pattern: preview by default, fail closed.
  3. Prove the script on a throwaway replay, as `ops/cleanup/verify-v5.4-cleanup.sh` does.
  4. Fahad approves the apply.
* **Never:** a title, pattern or date-range delete, or touching UNCERTAIN rows.

## H. Accidental owner decision or review record

* **Deliverables:** the Hub's drawer undoes pin, archive, approve and revision. Undoing sends `decision: null`, which clears the decision, key, note, author and time.

  Without the Hub, use one scoped update. It keeps the row and leaves it neutral; the constraint needs the decision and its key to be both set or both empty:
  ```sql
  update public.deliverable_reviews
     set decision = null, decision_key = null, decision_note = null, decided_by = null, decided_at = null,
         pinned = false, archived = false, updated_at = now()
   where project_id = '<project id>' and deliverable_key = '<deliverable key>';
  ```
* **Coding approvals** (`agent_approvals`):
  * An approval is consumed when it is used.
  * If an approved merge already merged, revert the PR (A or B).
  * If it was not consumed yet, cancel the session from the Hub before it runs.
* **Office approvals** (`approvals`): set the row to rejected before it is consumed.
* **Afterwards:** note the correction in the project so the audit trail explains it.
