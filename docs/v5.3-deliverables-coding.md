# V5.3 — Project Deliverables Center + simplified Coding workspace

Status: open PR from `claude/v5.3-deliverables-center`. Not merged, not
deployed. The one new migration is **not applied**. UI and Hub read layer
only: the Office engine, the Coding Agent controller, Continuity and every
production flag are unchanged.

## Deliverables Center

Where: the **Deliverables** tab of every project (`#/project/<id>/deliverables`)
and the primary navigation item **Deliverables / المخرجات** (`#/deliverables`,
current project). The Command Center stays the project default and its
artifacts card now links here. The file and export library stays at
`#/artifacts` ("All files & exports").

What a card is (real data only, `src/hub-deliverables.js`):

| Source | Card |
| --- | --- |
| Office task (specialist, research, CHIEF review/synthesis, direct with artifacts) | One card per version chain (`revisesTaskId`, synthesis rounds). It shows the newest delivered version; an older version stays one click away. |
| Coding Agent session | One card per task (cancelled sessions excluded), linked to the objective that launched it. |
| Artifact with no Office task | Its own card. |

Statuses: `needs_fahad`, `blocked`, `needs_review`, `in_progress`, `waiting`,
`ready`. Each comes with a machine reason that the client localizes (for
example: a decision is waiting, an approval, a question, the audit verdict is
NEEDS WORK, finance is INCONSISTENT, CI failed, waiting for free capacity, or
waiting for another employee). A card is never shown as finished when it is
not.

Previews come from the real artifact or result: a mini table, chart, kanban,
timeline, checklist, risk grid, finance KPIs, compliance counts, an audit
verdict, a report cover, or code chips and a file list. Work that has not
finished shows its state only, never a placeholder output.

Board tools:

* search;
* filters: employee, type, status, date, priority, objective, archived;
* sort: smart (pinned first, then what needs Fahad), newest, oldest,
  employee, status, type, title;
* views: grid, list and grouped (by employee, status, objective or type).

View choices persist per browser. The board refreshes in place on live events
(at most every 10 s) and polls only while work is active.

Details drawer: summary, visual outputs with the existing exports, the full
report, versions, links, then Fahad's decisions:

| Decision | What happens |
| --- | --- |
| Approve | Recorded on that exact version; optionally saved as a project decision (`/api/projects/<id>/memory`). |
| Request revision | Office: sent as a real direct conversation to the employee (CHIEF when the employee has no direct chat), and marked as revision requested once the new table exists. Coding: pre-fills the CODING composer. |
| Continue | Pre-fills a CHIEF conversation with the deliverable as context. |
| Coding approvals, questions, resume | The existing `/api/approvals/<id>` and `/api/tasks/<id>/reply` and `/resume` endpoints. |
| Pin, archive, undo | Recorded per deliverable. |

API (owner authentication as for every Hub route):

* `GET /api/deliverables?workspaceId=` returns the board.
* `GET /api/deliverables/report?workspaceId=&taskId=` returns one report, after checking it belongs to the project.
* `POST /api/deliverables/review` takes `{ workspaceId, key, pinned?, archived?, decision?, note? }`.

Reads are bounded like the other Office reads (60 jobs, 200 artifacts,
60 sessions, 500 results).

### Migration and degraded mode

`supabase/migrations/20261005160000_deliverable_reviews.sql` adds one
isolated, additive table, `public.deliverable_reviews`. It holds only Fahad's
curation: pin, archive, approved or revision requested, the exact version and
a note. It is service-role only with RLS on, cascades with its project, and is
never read by the Office or Coding engines. The scenario is
`supabase/verify/scenarios/deliverable_reviews.sql`; the fingerprint change is
additive.

Until Fahad applies it, everything else works. The board and drawer render;
Approve, Pin and Archive show as unavailable with an honest note; the endpoint
answers `503 DELIVERABLE_REVIEWS_UNAVAILABLE`. Request revision, Continue and
every coding decision do not need it.

## Coding workspace

`#/code` and `#/task/<id>` are now a calm, chat-like thread
(`src/hub-ui/coding.js`, loaded on demand). The thread reads in this order:

1. the request;
2. what CODING did (plan, last steps, current step);
3. the output (summary, pull request, CI, tests, deploy, files);
4. what is next (approve or reject, answer, resume, or "Done. Nothing needs you.").

Tabs: Overview, Activity, Files, Approvals. A banner jumps to whatever needs
Fahad, and a sticky composer replies into the same session.

Runtime internals live in **Advanced**, closed by default: the stage
timeline, engine and cost, models used, branches, the original instruction
and raw events. The home page is a single composer; repository, budget,
routing, test command and deploy sit behind the repository chip. Task lists
are split into needs you, in progress and recent.

Unchanged: the task, approval, reply, resume and cancel endpoints, the
controller and its events.
